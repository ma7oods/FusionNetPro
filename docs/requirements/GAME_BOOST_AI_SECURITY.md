# المتطلبات — Game Boost + AI Security Monitor

المصدر: تعليمات المستخدم في المحادثة بتاريخ 2026-10-23. هذا مستند متطلبات، وليس إعلانًا عن ميزات منفّذة. عند التعارض، تعليمات المستخدم الأخيرة والصريحة تتقدم على وثائق الفريق القديمة.

## 0. المنتج المطلوب

تطوير **نفس تطبيق FusionNetPro لويندوز**، لا أداة منفصلة، بوحدة متكاملة باسم **Game Boost + AI Security Monitor**. يجب فحص المشروع الحالي وفهم المعمارية والواجهات والاختبارات قبل التعديل، ثم خطة وتنفيذ مرحلي. المحافظة على ميزة الاتصال وDNS واجبة. يريد المستخدم برنامجًا صحيحًا وعمليًا ومثبّت **EXE** وتعليمات واضحة لكيفية تثبيته.

لا تُفسَّر عبارة «أفضل حلول الاتصالات العالمية» كإذن لوعد بخفض ثابت للبنق أو لتطبيق كل Registry tweak. يقاس الأثر الفعلي وتُعرض الحدود بصدق.

## 1. Game Mode — طلب المستخدم التفصيلي

- عرض العمليات التي تستهلك الشبكة فعليًا: اسم التطبيق، PID، المسار، الرفع والتنزيل الحاليان.
- لا تختلق قياسات عندما لا يتوفر مصدر صحيح. عرض عدد الاتصالات ليس قياس bytes/s، ولا يجوز توزيع إجمالي المحول على العمليات.
- يختار المستخدم عمليات الخلفية التي يرغب في حظر اتصالها **مؤقتًا أثناء اللعب**.
- الحظر عبر قواعد **Windows Firewall outbound** مخصصة للبرنامج، محدودة بالمسارات المعروضة في المعاينة.
- عدم قطع إنترنت الجهاز كاملًا أو تغيير Firewall العام أو القواعد التي تخص المستخدم.
- حماية اللعبة وعمليات النظام والخدمات الأساسية وDNS وتطبيقات الحماية. يجب أيضًا دراسة المشغّلات وanti-cheat وDNS proxies وVPN، وعدم اعتماد أسماء العمليات وحدها كدليل كافٍ.
- توضيح أن قواعد Windows Firewall عادة حسب EXE، فتؤثر على كل العمليات التي تستخدم المسار نفسه؛ PID يستخدم للعرض والتحقق من هوية العملية، وليس وعدًا بقاعدة PID.
- الفصل بين **الحظر الكامل** و**تقييد السرعة**؛ لا تعرض وجود حد لسرعة الشبكة ما لم يُنفّذ ويُختبر. تخفيض CPU/process priority ليس network throttling.
- عرض مدة الجلسة، السبب، التطبيقات والمسارات والقواعد والتغييرات المتخذة، ونتيجة الاستعادة.
- إعادة التحقق من PID ووقت البدء والمسار عند التنفيذ لمنع PID reuse وتغيّر الهدف بين المعاينة والتنفيذ.

## 2. Security Monitor

- فحص CPU وRAM والعمليات والخدمات والمهام المجدولة وStartup والتواقيع الرقمية ومسارات الملفات والاتصالات.
- استخدام أدوات Windows وواجهات Microsoft Defender الرسمية، ومنها **Get-MpComputerStatus** و**Get-MpThreatDetection**.
- التمييز بين حالة Defender، وقائمة التهديدات التاريخية، والتهديد النشط. وجود كشف سابق معالَج لا يعني إصابة حالية.
- دعم **Sysinternals Autoruns** و**Process Explorer** كأدوات رسمية اختيارية. لا تنزيل أو تثبيت أو قبول EULA أو تشغيل بصلاحيات عالية خفيةً.
- البحث عن مؤشرات متعددة للتعدين الخفي مثل XMRig؛ لا استنتاج الإصابة من CPU وحده أو اسم ملف وحده أو عدم التوقيع وحده.
- كل تنبيه يرتبط بالأدلة ومصدرها ووقت الملاحظة ومستوى الثقة وسبب التنبيه والخطوة المقترحة.
- لا تسمِّ نتيجة heuristic أو AI «تشخيصًا مؤكدًا». لا تخترع نسبة إصابة إحصائية.
- التواقيع: trusted/unsigned/invalid/unavailable حالات مختلفة. وجود شهادة داخل الملف ليس تحقق ثقة، والتوقيع الصحيح ليس شهادة خلو من malware.
- الوصول المرفوض والمهلات والبيانات الناقصة والتغطية المحدودة تظهر صراحةً؛ لا تعرض «الجهاز سليم» بناءً على فحص ناقص.
- التحليل لا يقتل عمليات ولا يحذف أو يعزل ملفات ولا يعطل خدمات أو Startup أو Defender.

## 3. AI Analysis

- واجهة موفر تحليل AI قابلة للتهيئة، لا ربط إلزامي بخدمة أو مفتاح بعينه.
- Codex أداة للتطوير؛ لا تفترض أن التطبيق يستطيع استخدام حساب Codex كـGPT API مجاني.
- الفحص المحلي والتقارير يعملان بالكامل بلا API وبلا مفتاح.
- التحليل السحابي اختياري فقط: يراجع المستخدم المزود والعنوان والنموذج و**البيانات الفعلية التي ستُرسل** ويوافق على إرسال تلك الحمولة.
- تعطيل الإرسال افتراضيًا، وعدم الإرسال عند Scan أو Export أو بدء التطبيق.
- تقليل البيانات افتراضيًا: لا أسماء مستخدمين أو مسارات كاملة أو IP عام أو machine IDs أو command lines أو محتوى ملفات أو مفاتيح. الإبقاء على البيانات المحلية الكاملة لا يبرر إرسالها للسحابة.
- تخزين آمن للمفاتيح، خارج السورس وFusionSettings JSON والسجلات ونسخ الإعدادات والتقارير.
- التصميم المقترح: DPAPI CurrentUser مع ربط المفتاح بمصدر المزود، HTTPS، حظر التحويلات التي قد تسرب المفتاح، حدود لحجم الطلب/الرد ومهلات وإلغاء.
- AI يعيد رأيًا وأدلة نصية للمراجعة فقط؛ لا يملك صلاحية أدوات أو إجراءات أو Firewall أو أوامر نظام.

## 4. Safety & Restore

- **الافتراضي قراءة وتحليل فقط.** لا تورّث automation القديمة التي تنفذ Fusion Mode الواسع دون مراجعة.
- قبل كل حظر أو تعديل: معاينة تطبيقات + مسارات + أسماء قواعد + النطاق + المدة + ما سيحدث عند Stop/تعطل/إعادة تشغيل، ثم موافقة واضحة.
- حفظ نسخة الحالة **بنجاح قبل إصدار أي تغيير**. إخفاق التسجيل يمنع الإجراء، ولا يكفي استدعاء Journal.Record إذا كان يخفي خطأ الحفظ.
- التراجع تلقائيًا عن قواعد FusionNetPro الخاصة بالجلسة عند نهاية اللعب أو تعطل التطبيق أو إعادة التشغيل.
- لا تحذف قواعد المستخدم، ولا القواعد الخاصة بجلسة/ميزة أخرى، ولا تغيّر حالة الجدار العامة.
- لا تتوقف Defender أو عمليات النظام. لا تستخدم Strict Lockdown العام لتنفيذ المتطلب.
- أقل صلاحية ممكنة؛ Scan عادي بلا admin متى أمكن، وUAC فقط عند إجراء يحتاجه فعليًا.
- لا تعتبر فشل استعلام القواعد قائمة فارغة سليمة، ولا تعتبر محاولة حذف غير مؤكدة استعادة ناجحة. احتفظ بالحالة المعلقة عند الفشل.
- تصميم استعادة التعطل يحتاج حسمًا موثقًا: قواعد Firewall الدائمة لا تزول بمجرد موت التطبيق. watchdog/استعادة عند تسجيل الدخول أو تصميم WFP لهما حدود مختلفة، ولا يجوز الادعاء بتحقيق الشرط قبل اختباره.

## 5. UI داخل التطبيق

- تبويبان/صفحتان: **Game Boost** و**Security Monitor** ضمن تنقل WPF الموجود.
- لوحة استهلاك وتنبيهات، مع أزرار **Scan** و**Start Game Mode** و**Stop & Restore** و**Export Report**.
- العربية واضحة وRTL ومتناسقة مع موارد الثيم الحالية، مع استمرار نمط AR/EN الموجود.
- فصل حالات loading/cancelled/partial/permission denied/unavailable عن النتائج السليمة.
- لا عمل ثقيل على UI thread؛ إلغاء متاح، عمليات الخلفية محدودة، ولا اشتراكات أو timers متراكمة عند التنقل.
- نموذج معاينة واضح قبل أي تعديل، وحوار مراجعة مستقل قبل كل إرسال AI.

## 6. Quality وقيود التطوير

- مراجعة المعمارية والواجهات والاختبارات أولًا، ثم خطة مكتوبة وتنفيذ مرحلي.
- اختبارات لمراقبة العمليات، قواعد الحظر، الاستعادة، الصلاحيات، الهوية، الموافقة، والبيانات غير المتاحة.
- شغّل اختبارات المشروع والتحقق من البناء، وسجّل النتائج الحقيقية والأوامر وحدودها.
- **لا فحص عميق أو تعديل إعدادات جهاز المستخدم الفعلية أثناء التطوير دون موافقته.** اختبارات الإنتاج الحية منفصلة عن الاختبارات الوهمية والكتابة في temp.
- لا تكسر فحص الاتصال أو DNS أو إصلاحات المثبّت والاستعادة الحالية.
- لا تحذف اختبارات أو تخفض الشروط للحصول على نجاح شكلي، ولا تضف اعتمادًا خارجيًا دون حاجة واضحة.

## 7. طلب سابق يجب حفظه: LibreHardwareMonitor

أمر المستخدم: «وهذه الأداة أيضًا أضفها للبرنامج» لنظام ويندوز:

https://github.com/LibreHardwareMonitor/LibreHardwareMonitor

- مطلوب دمج مراقبة العتاد داخل التطبيق. لم يثبت أو يدمج الاعتماد بعد.
- المراجعة وجدت الحزمة الرسمية LibreHardwareMonitorLib 0.9.6 وقت المراجعة؛ يجب التحقق مجددًا من النسخة والتوافق والتبعيات والتراخيص قبل الاعتماد النهائي.
- درجات حرارة CPU/GPU والحمل والمراوح/الحساسات حسب دعم العتاد؛ لا تنشئ قيمًا وهمية.
- لا تثبيت driver أو تغييرات مروحة أو voltages أو overclocking تلقائيًا. الصلاحيات أو المستشعرات غير المدعومة تُشرح.
- حساسات GPU الإجمالية لا تنسب استخدام GPU لعملية بعينها ولا تثبت وجود miner.
- يجب شحن MPL-2.0 والتراخيص والإشعارات للتبعيات كما يلزم، وربط المصدر الرسمي؛ لا مواقع غير تابعة للمشروع.

## 10. مخرجات التسليم المطلوبة في النهاية

- مصدر الوحدة ضمن المشروع نفسه، مرتبط بصفحات التطبيق وخدماته.
- اختبارات حقيقية ومكتوبة ونتائج موثقة، مع قائمة بما لم يُختبر على العتاد/الجدار الحقيقي.
- وثائق المتطلبات والحالة والتشغيل تبقى قابلة للاستكمال من أي نموذج.
- EXE للتشغيل وEXE للتثبيت، مع إصدار متطابق وبصمات وملفات تراخيص الاعتمادات، وتعليمات تثبيت عربية.
- لا تسلّم ملفًا قديمًا باسم الإصدار الجديد أو تدّعِ أن ملفات dist تتضمن ميزات غير مبنية.
